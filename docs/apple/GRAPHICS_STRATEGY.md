# Native DXVK and Apple graphics

Current checkpoint: Phase 6 owner acceptance is recorded in [IOS_GAMEPLAY.md](IOS_GAMEPLAY.md); Phase 7 is authorized and its performance results are in [PHASE7_STATUS.md](PHASE7_STATUS.md). Earlier pending/not-started statements below describe historical checkpoints.

The graphics target is guest D3D9 → DXVK Native → Vulkan on Metal. Keep backend selection in the native renderer and give the platform implementation ownership of the presentation layer.

## Existing integration

- [d3d9_dxvk.c](../../android/host/d3d9_dxvk.c) exposes x86 D3D9 COM objects via guest vtable/thunk records. [bridge.cpp](../../android/dxvk/bridge.cpp) invokes native COM slots and converts structures, handles, pitches and references. Lock/unlock copies explicitly reconcile guest and native memory. Keep guest layout, calling conventions, HRESULTs, references, queries and lifetime tests.
- The bridge acquires `ANativeWindow` leases, looks up the native D3D9 DSO and loads `Direct3DCreate9` and the callback registrar. Android's [WSI](../../android/dxvk/wsi_android.cpp) advertises `VK_KHR_surface` and `VK_KHR_android_surface` and creates the surface using `vkCreateAndroidSurfaceKHR`. It also supplies display/window methods to DXVK. The [build overlays](../../tools/build_dxvk.py) inject the Android WSI bootstrap and Vulkan loader callback and control shared-library exports. Separate those responsibilities from the marshaling and renderer logic.
- The recipe overlays scaled vertex format and SPIR-V handling, query pool allocation, pipeline cache and worker/present notifications. Vulkan loader/Turnip choices and PowerVR workarounds have platform or driver predicates. Retain the optimizations and test their applicability. Check cache keys with driver UUID, build revision and settings changes.
- The alternative EGL/GLES path shares D3D9 files, headers and scheduler code. Audit those dependencies to identify the portable shader, format, texture and render-command logic. Phase 3 must exercise DXVK on Apple.

## Metal WSI design

1. AppKit owns a layer-backed view on the main thread. Use a view-owned `CAMetalLayer`, publish drawable extent in backing pixels, resize generation, visibility/focus and stable identity. Pass a retained opaque presentation target to DXVK. Hold the reference until the swapchain and surface have been destroyed. Test main-thread UI ownership and render-thread teardown ordering. Later, UIKit supplies the same contract through its view layer. [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)
2. Resolve `vkGetInstanceProcAddr` from the pinned loader/backend path. Keep Vulkan dispatch and selected ICD in the native platform configuration. Advertise `VK_KHR_surface` and `VK_EXT_metal_surface` when present. Resolve `vkCreateMetalSurfaceEXT` from that instance and pass the leased layer via `VkMetalSurfaceCreateInfoEXT`. Check the present queue, format/color space, extent, composite alpha, image count and supported present modes before swapchain creation. [Vulkan Metal surface extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_metal_surface.html)
3. With a loader that filters portability devices, enable `VK_KHR_portability_enumeration` and set `VK_INSTANCE_CREATE_ENUMERATE_PORTABILITY_BIT_KHR` when advertised and needed. Enable `VK_KHR_portability_subset` when the selected device advertises it and query its features and properties. Apply both decisions where DXVK creates its own Vulkan objects. Log actual extension names, feature values, queue selection and failures. [MoltenVK loader guidance](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md), [Vulkan portability subset](https://docs.vulkan.org/refpages/latest/refpages/source/VK_KHR_portability_subset.html)
4. Use a Mach-O export and loader setup for the D3D9 entry and callbacks. Build Mesa and MoltenVK configurations independently against pinned headers. Recheck surface generation, resize and backing scale, and the actual `VK_SUBOPTIMAL_KHR`/`VK_ERROR_OUT_OF_DATE_KHR` paths on hide, minimize, resume and device reset. On iOS, evaluate a linked MoltenVK slice or sanctioned embedded framework using the same Vulkan function interface.

## Compatibility questions

Mesa documents KosmicKrisp on Apple Silicon with Metal 4 and macOS 26+. Its driver documentation currently reports no iOS support. MoltenVK documents macOS and iOS presentation. Both are macOS candidates, with MoltenVK the iOS starting point. The audit ran neither backend and made no driver selection. [Mesa driver docs](https://docs.mesa3d.org/drivers/kosmickrisp.html), [MoltenVK Runtime User Guide](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/MoltenVK_Runtime_UserGuide.md)

## Phase 3 M4 implementation and findings

AppKit retains a CAMetalLayer through a presentation target with an atomically published drawable extent. DXVK's Apple WSI consumes that target through an opaque window lease, enables the Metal surface extensions and enables Vulkan portability enumeration and its device subset when advertised. The existing typed COM bridge still marshals all guest pointers and structures. Vulkan loader and ICD selection remain external to the guest and interchangeable by environment. The validated backend is KosmicKrisp on the M4.

Both SDK ICDs presented a 640×400 clear with exact RGB readback and reported BC texture compression and precise occlusion. Both exposed D32S8. The Vulkan probe returned no D24S8 support. KosmicKrisp then passed DXVK's D3D9 D24S8-compatible allocation, BC1 and BC3 format checks, texture write, SM3 draw, occlusion and queue present. MoltenVK could present a standalone swapchain. DXVK's device creation still returned `D3DERR_NOTAVAILABLE` because that ICD lacks `robustBufferAccess2` and `nullDescriptor`. This DXVK backend has no dummy descriptor fallback for its robustness requirements.

Both ICDs lack geometry shaders. DXVK's layered copy, blit and resolve use its existing vertex-layer shaders where `shaderOutputLayer` is available. The Apple overlay reports `D3DERR_NOTAVAILABLE` for geometry-dependent ProcessVertices or non-solid fill when the required device feature is absent. KosmicKrisp's validated path uses solid fill. Fullscreen display mode switching and an alternative wireframe path remain open.

The first game launch rendered into a D3D9 back buffer after startup, approximately 24 seconds after process launch. A process sample showed subsequent frames making progress through DXVK's swapchain blitter, Vulkan validation and Metal command encoding. On that run the validation layer flagged `06479` for BC1, BC3, BGRA8 and RGBA16F color views sharing the descriptor used by DXSO comparison instructions. DXSO can dynamically select an ordinary or comparison sample from the same guest sampler. The original descriptor exposed the color view to both instruction forms. The Apple overlay allocates comparison bindings separately and populates them only for the corresponding depth texture. This preserves runtime depth selection and avoids invalid color bindings. A fresh validated run produced the first frame again in about 7.6 seconds from launch and reported zero Vulkan validation errors. That timing also includes native startup, asset load, and first pipeline compilation. The two elapsed times were gathered on separate runs and do not isolate a performance gain from the descriptor change.

The corrected game run emitted ten warnings for an unused fragment color output during a depth-only draw. The file capture is the first 640×480 non-uniform UT3 back buffer after guest draws and a successful D3D9 Present submission. The Vulkan log separately confirms the first accepted queue present to a 960×540 CAMetalLayer swapchain. UT3 rendered its startup CD Key screen. Input, authentication, normal menu transitions and gameplay remain for later validation. Game capture used UE3's audio-disabled startup option and the existing DirectSound compatibility mixer with no hardware output connected. The local Steam game files supplied the SM3 reference shader cache. Cooked shaders rendered in this run. Runtime D3DX HLSL compilation on macOS and cold uncached shaders remain open.


## Phase 6 measured iPhone result (2026-11-17)

On the physical A19 Pro/iOS27.0.1, MoltenVK1.4.2 passed VK_EXT_metal_surface swapchain clear, exact pixel readback and presentation. The same app then loaded the native iOS DXVK slice and exercised the existing D3D9 COM fixture. CreateDevice failed with VK_ERROR_FEATURE_NOT_PRESENT: robustBufferAccess2=0 and nullDescriptor=0. Extension-name support alone was insufficient. Preserve DXVK correctness requirements; investigate real semantics in the driver or a tested DXVK compatibility implementation before changing feature requests. This is a Phase6 blocker, not a UT3 rendered-frame milestone. Details and pending checks: [PHASE6_STATUS.md](PHASE6_STATUS.md).


## Phase 6 continuation: explicit D3D9 compatibility

The initial missing-feature failure is superseded by the D3D9 fallback in [D3D9_PORTABILITY.md](D3D9_PORTABILITY.md). Driver capability bits remain false; explicit constant bounds and typed read-only dummy descriptors supply the required D3D9 behavior. Exact ARGB tests, dynamic sampler selection, COM creation/draw/query/Present and 720p/1080p resets pass with Metal API/GPU validation. An ordinary run captured the first real UT3 back buffer on the iPhone. Real-game validation then caught heap aliasing during upload; the dedicated-image correction now passes two real-game frame-capture/exit runs with Metal API and GPU shader validation enabled. The original aliasing assertion did not recur. Existing guest DLL-detach heap-free warnings remain documented. Full Phase 6 gameplay/input/audio/lifecycle remain pending, and Phase 7 is not started.
